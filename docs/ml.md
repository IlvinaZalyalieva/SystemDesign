# CV/ML подходы в системе распознавания лиц

## CV/ML задачи и выбранные подходы

### 1. Детекция лица
**Задача:** Найти все лица на кадре с камеры.
**Подход:** MTCNN для MVP, RetinaFace для production.
**Обоснование:** MTCNN хорошо работает на разнообразных данных, имеет баланс точности и скорости. RetinaFace даёт лучшую точность на сложных ракурсах и условиях освещения.
**Метрика:** mAP@0.5 > 0.95 на валидационном наборе.

### 2. Оценка качества кадра
**Задача:** Определить, подходит ли кадр для распознавания.
**Подход:** Комбинация правил и модели.
- **Правила:** яркость, контраст, размытие, размер лица, ракурс
- **Модель:** LightGBM/CNN для комплексной оценки
**Обоснование:** Правила быстрые и интерпретируемые, модель улавливает сложные паттерны.
**Метрика:** F1-score > 0.9 на размеченных данных.

### 3. Face alignment
**Задача:** Выровнять лицо по ключевым точкам.
**Подход:** 5-point или 68-point landmark detection.
**Обоснование:** Выравнивание критично для стабильности эмбеддингов.
**Модель:** MobileNet-based landmark detector для скорости.

### 4. Liveness / Anti-spoofing
**Задача:** Отличить реальное лицо от фото/видео/маски.
**Подход:** Мультимодальный:
- **Правила:** моргание (eye aspect ratio), микродвижения головы
- **Модель:** CNN на патчах лица (текстура кожи, отражения)
- **Hardware:** ИК камера для depth sensing (для production)
**Обоснование:** Defense in depth. Правила ловят простые атаки, модель - сложные.
**Метрика:** Attack Presentation Classification Error Rate (APCER) < 0.1%, Bona Fide Presentation Classification Error Rate (BPCER) < 5%.

### 5. Извлечение эмбеддинга
**Задача:** Преобразовать выровненное лицо в вектор признаков.
**Подход:** ArcFace (InsightFace) или AdaFace.
**Обоснование:** ArcFace показывает SOTA на стандартных бенчмарках (LFW: 99.83%), AdaFace лучше на низкокачественных данных.
**Размерность:** 512 или 1024 dim, зависит от tradeoff точность/память.

### 6. Сравнение с базой (Verification vs Identification)
**Verification (1:1):** "Это сотрудник X?" - проверка против конкретного эмбеддинга.
**Identification (1:N):** "Кто это?" - поиск среди всей базы.

**На проходной нужен Identification:**
- Сотрудник не предъявляет ID
- Система должна определить, кто подошёл к турникету
- Но после матчинга выполняется verification против найденного кандидата

**Подход:** One-to-many поиск с порогами:
1. Поиск k nearest neighbors в ANN-индексе
2. Расчет similarity score = 1 - distance (cosine similarity)
3. Применение порогов: allow_threshold > review_threshold > deny_threshold

## Поиск one-to-many на больших базах

**Проблема:** Полный перебор O(N) неприемлем для 100k+ записей и <1 секунды.

**Решение:** Approximate Nearest Neighbor (ANN) индекс:
- **FAISS (Facebook)** для MVP: IVF + PQ, GPU поддержка
- **ScaNN (Google)** для production: лучшее качество/скорость
- **Параметры:** nlist=4096, nprobe=32 для recall@1 > 0.99

**Архитектура поиска:**
1. Иерархический: локальный кэш (10k) → центральная база (100k+)
2. Мультитенантный: отдельные индексы для разных площадок
3. Инкрементальное обновление: добавление/удаление без полной переиндексации

## Выбор порогов для allow/review/deny

### Tradeoff: False Accept vs False Reject

**False Accept (FA):** Посторонний проходит как сотрудник.
- **Цена:** Высокая - инцидент безопасности (~500 000 ₽)
- **Цель:** FAR < 0.1% (1 на 1000)

**False Reject (FR):** Сотруднику отказано в доступе.
- **Цена:** Средняя - потеря времени, недовольство (~120 ₽/случай)
- **Цель:** FRR < 5%

### Критерии решений:

1. **Allow:** 
   - quality_score > 0.8
   - liveness_score > 0.9  
   - match_score > 0.85
   - margin_to_second_best > 0.1

2. **Manual Review:**
   - 0.7 < quality_score ≤ 0.8
   - 0.8 < liveness_score ≤ 0.9
   - 0.75 < match_score ≤ 0.85
   - 0.05 < margin_to_second_best ≤ 0.1
   - Любое сочетание пограничных значений

3. **Deny:**
   - quality_score ≤ 0.7
   - liveness_score ≤ 0.8
   - match_score ≤ 0.75
   - margin_to_second_best ≤ 0.05

**Калибровка порогов:**
- На исторических данных с метками
- ROC curve анализ для выбора operating point
- Адаптация под конкретную проходную (освещение, камера)

## Правила vs Модели

**Правила (используются когда):**
- Быстрая проверка (яркость, размер лица)
- Интерпретируемость критична (объяснение отказа)
- Простые пороги (quality < 0.7 → manual_review)

**Модели (используются когда):**
- Сложные паттерны (liveness, spoofing)
- Многомерные решения (комбинация факторов)
- Адаптация к данным (дрифт освещения)

## Готовые vs собственные модели

**Готовые предобученные модели:**
- Face detection (MTCNN, RetinaFace)
- Face recognition (ArcFace, AdaFace)
- **Плюсы:** Быстрый старт, SOTA качество
- **Минусы:** Может не подходить под конкретные условия

**Собственные данные нужны для:**
1. **Дообучение recognition модели** на сотрудниках компании
   - Fine-tuning последних слоёв
   - Улучшение на специфичных условиях (униформа, освещение)
2. **Обучение liveness модели** на реальных атаках
   - Сбор датасета spoofing атак
   - Domain adaptation под конкретные камеры
3. **Quality assessment модель** под условия проходных

## Baseline подходы

**Первый запуск (2 недели):**
1. MTCNN + ArcFace (готовые модели)
2. Правила для quality assessment
3. Простые правила liveness (моргание)
4. FAISS индекс на эмбеддингах сотрудников
5. Консервативные пороги (высокий review rate)

**Второй этап (1 месяц):**
1. Сбор валидационного набора
2. Калибровка порогов по данным
3. Добавление lightGBM для quality
4. Простая CNN для liveness

**Production (3 месяца):**
1. RetinaFace + AdaFace
2. Мультимодальная liveness (правила + CNN + ИК)
3. ScaNN индекс
4. A/B тестирование новых моделей

## Технические метрики для выбора

1. **Распознавание:**
   - FAR/FRR при разных порогах
   - Equal Error Rate (EER)
   - ROC AUC, Precision-Recall AUC
   - Recall@1 (для identification)

2. **Liveness:**
   - APCER/BPCER
   - Attack detection rate по типам атак

3. **Производительность:**
   - P50/P95/P99 latency каждого компонента
   - Throughput (кадров/секунду)
   - Потребление памяти/GPU

## Валидационный набор и сплиты

**Принципы:**
1. **Split by identity, not by frames:** Все кадры одного сотрудника в одном сплите
2. **Temporal split:** Старые данные в train, новые в val/test
3. **Camera split:** Разные камеры в разных сплитах
4. **Condition split:** Разные условия освещения в разных сплитах

**Размеры:**
- Train: 70% сотрудников (разные камеры, дни)
- Validation: 15% сотрудников (для калибровки порогов)
- Test: 15% сотрудников (hold-out для финальной оценки)

**Leakage prevention:**
- No same identity across splits
- No temporal leakage (future data in train)
- No camera leakage (та же камера в train и test)

## Обработка delayed labels

**Источники delayed labels:**
1. Ручные проверки охраны (через 1-5 минут)
2. Жалобы сотрудников (через часы/дни)
3. Проход по карте после отказа (instant)

**Pipeline обработки:**
1. **Streaming:** Логи событий → Kafka
2. **Enrichment:** Добавление delayed labels при поступлении
3. **Retraining:** Еженедельное переобучение на обогащённых данных
4. **Shadow evaluation:** Новая модель vs старая на свежих данных

**Метрики на delayed data:**
- Confusion matrix с delayed labels
- Анализ false accept через security incidents
- Анализ false reject через жалобы

## Нужен ли LLM в системе?

**Нет, LLM не нужен в контуре решения allow/deny.**

**Причины:**
1. **Детерминизм:** Решения доступа должны быть воспроизводимы и аудируемы
2. **Латентность:** LLM инференс добавляет сотни мс
3. **Безопасность:** LLM может быть обманут prompt injection
4. **Регуляторные требования:** Биометрические решения требуют сертификации

**Где LLM может быть полезен (вне контура):**
1. **Генерация объяснений** для охраны: "Отказ из-за низкого качества кадра (контровый свет)"
2. **Анализ инцидентов:** Поиск паттернов в audit log
3. **Обучение охраны:** Симуляция сложных кейсов
4. **Документация:** Автоматическое обновление runbooks

**Вывод:** LLM - вспомогательный инструмент для эксплуатации, но не для принятия решений о доступе.
