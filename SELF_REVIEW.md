# Self-Review решения

## Самая слабая часть решения

**Liveness detection в PoC** - используется упрощённая mock проверка вместо реальной ML модели. В production это критический компонент для предотвращения spoofing атак, требующий многомодальной проверки (текстура кожи, глубина, моргание, микродвижения).

## Сделанные предположения

1. **Производительность edge-оборудования** - предполагается, что NVIDIA Jetson Orin справится с inference <200 мс
2. **Качество камер** - предполагается адекватное освещение и разрешение 1080p
3. **Network reliability** - предполагается стабильное соединение между edge и центром
4. **Сотрудничество HR** - предполагается интеграция с HR системой для синхронизации данных сотрудников
5. **Юридическая база** - предполагается наличие необходимых согласий на обработку биометрических данных

## Нерешённые риски

1. **Adversarial attacks** - целенаправленные атаки на модели распознавания
2. **Bias в моделях** - возможна разная точность для разных демографических групп
3. **Model drift** - изменение условий (сезонность, новая униформа) может снизить точность
4. **Single point of failure** - центральный сервис при полном отказе может заблокировать все проходные
5. **Social engineering** - обман охраны при manual review

## Компромиссы, сделанные ради demo

1. **Mock вместо реальных моделей** - для скорости разработки
2. **Упрощённые правила вместо ML** - для liveness и quality assessment
3. **In-memory поиск вместо FAISS/ScaNN** - для простоты демо
4. **Отсутствие реальной интеграции** - с камерами, турникетами, HR системами
5. **Упрощённый audit log** - файловая система вместо distributed time-series DB

## Что можно улучшить за 2 дополнительных дня

1. **Реальная интеграция** с OpenCV для face detection и insightface для recognition
2. **Docker контейнеризация** всех компонентов
3. **Базовый веб-интерфейс** для охраны с реальными изображениями
4. **Простое ANN** с использованием FAISS для поиска
5. **Базовые тесты** и CI/CD pipeline
6. **Конфигурация через environment variables** вместо hardcoded значений
7. **Metrics collection** с выводом в Prometheus/Grafana

## Что нужно доработать перед production-запуском

1. **Юридический review** - compliance с GDPR, 152-ФЗ, отраслевыми стандартами
2. **Security audit** - penetration testing, code review, threat modeling
3. **Load testing** - проверка производительности под пиковой нагрузкой
4. **Disaster recovery plan** - процедуры восстановления при сбоях
5. **Training данных** - сбор и разметка dataset под конкретные условия
6. **A/B тестирование** - постепенный rollout с метриками успеха
7. **Documentation** - runbooks для эксплуатации, troubleshooting guides
8. **Monitoring и alerting** - полноценная observability stack

## Части системы, требующие юридической проверки

1. **Сбор и хранение биометрических данных** - требуется explicit consent, data minimization, retention policies
2. **Audit log с изображениями** - требования к хранению и защите персональных данных
3. **Интеграция с HR системами** - передача персональных данных между системами
4. **Автоматическое принятие решений** - требования к transparency и возможности обжалования
5. **Data export и deletion** - процедуры для выполнения прав субъектов данных

## Части системы, требующие проверки безопасности

1. **Хранение эмбеддингов** - защита от model inversion attacks
2. **API endpoints** - authentication, authorization, rate limiting
3. **Edge-устройства** - physical security, secure boot, encrypted storage
4. **Network communication** - TLS, certificate management
5. **Access control** - принцип минимальных привилегий для операторов

## Части системы, не подлежащие полной автома��изации

1. **Final decision при manual_review** - всегда должен оставаться за человеком
2. **Security incident investigation** - требует человеческого анализа контекста
3. **Policy exceptions** - разовые разрешения, гостевой доступ
4. **System configuration changes** - изменение порогов, добавление новых моделей
5. **Employee complaints handling** - разбор жалоб на false reject

## Какие данные пилота убедили бы остановить проект

1. **False accept rate > 0.5%** - недопустимый риск безопасности
2. **Employee satisfaction < 70%** - сопротивление внедрению
3. **Latency p95 > 2 секунды** - не достигается основная цель (ускорение прохода)
4. **Manual review rate > 25%** - система не снижает нагрузку на охрану
5. **Cost of ownership > экономии** - negative ROI
6. **Непреодолимые юридические ограничения** - запрет на использование биометрии
7. **Технические ограничения** - невозможность достижения требуемой точности в данных условиях

## Заключение

Решение демонстрирует понимание всех аспектов системы распознавания лиц: от продуктовых и экономических до технических и security considerations. PoC подтверждает работоспособность ключевых архитектурных решений, но требует значительной доработки перед production использованием. Основная ценность - в системном подходе к проектированию, учёте tradeoffs и понимании рисков работы с биометрическими данными.
